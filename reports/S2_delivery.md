## 一、S2 范围复核（**偏离原计划 3 项，先说为什么**）

ARCH-01 给 S2 列了四项。S1 完成后逐条复核，只有两项仍然成立：

| 原计划项 | 复核结论 | 理由 |
| --- | --- | --- |
| XAML 抽独立文件 + 构建时内联 | **推迟到 S4** | 交付物必须是单个 `.ps1`（桌面快捷方式与 `launch_app.vbs` 直指该文件），抽文件就必须引入 `src/ → build.ps1 → 单文件` 构建链；当前**没有版本控制**，源与产物一旦分叉无法回溯，风险大于可编辑性收益。S4 会先落构建链与行号映射，再拆 XAML |
| `-LibraryOnly` 无 UI 模式 | **推迟** | 它要求把 2000 行顶层执行语句收进 `Initialize-Ui`，改动面接近半个架构重构；而其目标（数据层可无窗口测试）S0 已用「提取函数块 dot-source」达成，收益不成立 |
| 轮询改「偏移驱动 + 2 秒兜底」 | **不做** | S1 之后轮询本身已是 5–6 ms（指纹命中），事件驱动收益趋零；且 `FileSystemWatcher` 的可靠性问题 ARCH-01 已否决。保留 2 秒兜底更稳 |
| `Read-MergedFeed` 增量合并 | **采纳，已实施** | 实测文件一变化就要 54 ms（693 条对象重建 + 全量排序），是 S1 之后唯一的 O(N) 热点，且随消息数线性恶化 |
| 归档流程接入 `Reset-JsonlCache` | **采纳，已实施** | 有 `Reset-JsonlCache` 才敢安全重写 `board.jsonl`，这是 S1 留下的尾巴 |

## 二、改动一：合并热路径增量（主脚本，SHA `0BE340D3…` → `5478CAC9…`）

- 抽出 `New-BoardEntry`：把「一条板帖 → 一条时间线条目」的构造（含 57 号首行简报规则）收成一处，增量与全量共用，避免两处规则漂移。
- `Read-MergedFeed` 增加增量分支：当 **feed 未变 + board 只增不减 + board 读取模式为 `cache`/`append`** 时，只对新增板帖构造条目并**有序尾插**；否则回退全量重排。
- 安全阀：新增条目的 `when` 若早于已有最大值（不同进程时钟乱序、跨天修正），立即回退全量重排，绝不做错误的尾插。
- 全量路径改为先排序再存 `MergedState.Items`，使增量分支始终基于有序列表追加。

**性能（693 条规模，追加 1 行后）**

| | 改前 | 改后 |
| --- | --- | --- |
| 合并耗时中位 | 54 ms | **11 ms** |
| 缓存命中（无变化） | 6 ms | 5 ms |

约 5 倍改善，且不再随消息数线性增长（54 ms 那部分来自 693 次对象构造与排序）。

设计取舍：

## 五、风险与已知边界

- **增量合并依赖 append-only 与时间递增**：时间戳回退时自动回退全量，代价是一次全量重排（~54 ms），不会产生错误顺序。
- **归档后运行中的实例看不到变化**：`board.jsonl` 被重写，内存里的 `FileState`/`MergedState` 仍是旧数据。必须重启应用（或调用 `Reset-JsonlCache`）。当前你的窗口若还开着，需重启才看到 526 行版本。
- **`n` 序号语义**：增量分支的 `n` 继续递增（而非像全量那样按 feed→board 重排）。仅当同一秒内同时有 feed 与 board 新消息时，极端情况下相对次序可能与全量不同；`when` 不同则完全一致。已有「增量 vs 全量逐条一致」测试守住常规路径。
- **S1 的 Tail 局限仍在**：文件中间就地编辑察觉不到，依赖 `Reset-JsonlCache`。
