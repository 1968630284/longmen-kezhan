## 1. 做了什么

对标 IM 通用惯例（同一发送者约 60 秒内连续消息合并成视觉簇、时间戳 gutter、跨天日期分隔、系统消息中性居中），但按方案里已收窄的范围实施：**只做分组与时间格式，不推翻 QQ 风气泡体系、不改数据结构、不改外部协议**。

1. **两个纯函数放进数据层**（`src\10_data.ps1`，`UI-02 纯函数区`，不依赖 WPF）：
   - `Format-UiTime`：把 `20:36:00` / `2026-11-06 23:28:54` / 旧连字符写法 `20-50-03` 统一成 `HH:mm`；先按日期解析，失败再按开头时分兜底，都不匹配则原样返回。
   - `Test-UiGrouping`：同一发送者、同一天、间隔 0–60 秒、非系统消息、非搜索态、时间不倒退 → 合并。规则只在这一处定义。
2. **渲染层低风险参数化**：`New-MsgBubble` 加第 7 个可选参数 `[bool]$Compact = $false`。紧凑时头像 `Visibility="Hidden"`（**保留 34px 占位**，保证同簇气泡对齐）、不重复显示「角色 · 时间」行、上下边距收窄。传菜口 / 协作台的另一处调用点不传参数，**行为完全不变**。
3. **`Refresh-Feed` 分组与日期分隔**：整块重建时重置分组状态；循环里按 `when` 判断跨天并插入居中日期分隔（今天 / 昨天 / M月d日），再调用 `Test-UiGrouping` 决定是否紧凑。系统消息会重置分组；搜索态不分组也不插分隔；增量追加时用脚本级 `$script:UiPrev*` 跨轮保持状态，不会在新消息到达时把一簇拆开。
4. **一次性渲染诊断**：每进程只往 `health\ui.log` 写一行 `ui-render items=N compact=N dividers=N`，不随 2 秒轮询刷屏。

## 3. 边界与如实说明

1. **截图无法目视验证分组**：`reports\ui_UI02_grouping.jpg` 里窗口右半超出缩放后画面、气泡主体被裁在屏外，只能看到标题栏、系统消息和导航。因此分组生效与否**以 `ui-render` 诊断数字 + 40 项特征测试为准**，不假装截图已证明。
2. **增量追加未做长时间观察**：状态跨轮保持的逻辑已写，但只验证了单次启动；长时间运行下新消息续接同一簇的行为未做端到端计时观察。
3. **分组不改变消息文本序列**：`Compact` 只影响头像与 meta 的可见性，气泡正文仍逐条构造；Pester 的数据层黄金断言（条数、排序、字段）全部保持 25 项原口径通过。
4. **日期分隔依赖 `when`**：feed 里只有 `HH:mm:ss` 的历史消息由 `Convert-FeedTime` 补成「今天」，板上帖用真实日期，因此分隔按排序后的日期变化插入；不保证与每条消息的真实发送日完全一致，这是既有数据模型的限制。
5. Analyzer 告警从 175 增到 178（新增 3 条，仍是空 catch / 命名类），仅记录不设门禁。
6. 本次 `boot-feed-ready 2140ms` 低于上一轮的 3385/4599ms，但不排除热启动差异，**不作为性能提升结论**；紧凑消息减少的控件数也未单独计时。
