## 1. 项目总览

### 1.1 龙门客栈是什么

一个**单人 + 双 AI 的协作实验**，载体是一个自制的 Windows 桌面应用「龙门客栈」（单文件 PowerShell + WPF，`D:\tmp\xiaozhu_live.ps1`，现役 133,669 字节）。应用不是目的，是三人组的"店面"：

- 把云端 AI 的对话流、本地总线留言、视频任务状态，合成一条时间线给客官看；
- 让客官在窗口里直接发消息（双写：一份进云端对话流，一份进总线）；
- 承载视频生成工作流（Job 包 → 云端生成 → 回执对账 → 成品播放）。

另有两条并行战线：**微信线**（客官在手机上给本地 agent 发微信即可开回合）与**存档/搬家体系**（把全部上下文打成自包含包，供新会话或外部 AI 接手）。

### 1.2 三方角色与效力层级

| 角色 | 是谁 | 形态 | 职责 | 效力 |
| --- | --- | --- | --- | --- |
| 客官 | Dave，学生 | 真人，微信/桌面直说 | 定方向、拍板、验收最终结果、扫码填表这类只有人能做的事 | L1（最高业务效力） |
| 掌柜 | 小猪，云端 AI | 远程 Linux VM，经 Tailscale+SSH 摸到 PC | 把客官的话核成单子、派单、监督、验收、向客官汇报 | L2 |
| 大厨 | LOCAL，本地 AI | PC 上 DSH 桌面档/微信档 | 照单执行、带证据交工、卡住先问，不改范围不做决定 | 执行 |

技术上的层级更硬：**L0 常驻规则**（DSH 内置 + `~/.dsh/AGENTS.md` 驻地规矩）> **L1 客官直接指令** > **L2 总线/掌柜单据**。冲突时停手、记总线、等客官裁决，不许自行裁决。

### 1.3 为什么这么组织

- **AI 不能自己起回合**：本地 agent 是回合制的，没有外部输入就不思考、不看总线。所以必须有一个"人"当唤醒器——这就是客官在微信发一句话的全部作用。
- **云端模型适合规划与验收，本地模型适合动手**：掌柜能长时间在线盯流程，大厨能开窗口、跑脚本、截屏、读文件。分工按"能不能碰到东西"切，而不是按能力高低切。
- **一切写进文件**：两条会话线（桌面线/微信线）上下文不互通，聊天记录不可依赖，只有总线、账本、交接文件、存档包能跨线传递。这条约束塑造了整个档案体系。

## 2. 协作流程全图

### 2.1 名义流程

```
客官下单(微信一句话/一个数字)
  → 掌柜核成单子(kind=task, 七段模板)  → 发总线
    → 大厨每回合先 bus_inbox 捞单
      → 大单先审单(kind=discuss: 可行性/坑/更优做法)
        → 掌柜确认或改单
          → 大厨开火(claim → 改 → 自测 → parse/哈希校验 → release → log)
            → 交工帖(kind=result: 状态+做了什么+证据路径)
              → 掌柜按验收标准逐项核
                → 通过=结案 / 不达标=回锅(写明哪项不行)
```

### 2.2 实际运转里的六个真实环节

1. **口令接力**：客官打字慢，通常只说编号（"15"）。掌柜负责把编号还原成单据，大厨负责按编号找单。客官会**重复发同一个数字催办**，直到该项验收通过才换下一个号——这实际上是一个"数字心跳"协议，也是我方判断优先级的最强信号。
2. **总线**：`D:\tmp\nailong\bus\board.jsonl`，一行一条 JSON（ts/from/to/kind/text/ref/id）。247 条消息、时间戳连续可查，是唯一的正式档案。微信只是传话管子，不作数。
3. **桥（dsh-bus-bridge 插件）**：把总线接进 DSH 的工具体系，提供 `bus_inbox` / `bus_post`、回合镜像（activity.jsonl）、软唤醒（回合结束时把待办单子递进当前会话）。现役 v0.2.1，单子识别抬头现为「【掌柜 → 大厨】」。
4. **岗哨**：掌柜侧 30 秒一轮扫总线，命中关键词（准备好/等你/请查收/递单/联调/收货/videojob）即立即处理。这是"云端不掉线"的补丁。
5. **常驻规则**：五条驻地规矩写在 `~/.dsh/AGENTS.md`（用户全局，对本机所有 DSH 会话线生效）+ 微信线工作区 `AGENTS.md`（同文副本），每回合由 DSH 自动注入 system 侧。规矩只有客官能改。
6. **存档与搬家**：每次大改后打包 `D:\tmp\nailong\archive\<stamp>\`（BOOT + manifest + 全量件），新会话靠读包开局。这是跨会话记忆的唯一可靠通道。

### 2.3 每一步的真实耗时与卡点（实测数据）

| 环节 | 承诺 | 实测 | 卡点原因 |
| --- | --- | --- | --- |
| ACK（接单确认） | ≤2 分钟 | 首单约 35 秒；正常 1 分钟内 | 客官一句微信到 agent 起回合有几十秒延迟（WS 连接 + 模型首字） |
| 交工 | ≤15 分钟 | 单视图改版 5–15 分钟；4-补4 超时约 11 分钟；6 号 PC 段超时 | 改 WPF 脚本必须重启应用验证，重启+截图+哈希一轮约 3–5 分钟；返工叠加 |
| 验收 | 无明文时限 | 数分钟到数小时 | 掌柜也要起回合；客官不在时单据停在"待试菜" |
| 审单 | 无时限 | 5–20 分钟 | 需先查证据再写意见，纯思考 |
| 一次 UI 微调（客官要的"一条线"） | — | 平均 15–40 分钟 | 定位根因占 80% 时间（见 6.4 闭包、6.9 白线系列） |

**结论性观察**：整条链里最快的是执行，最慢的是"人不在"。15.8 小时里，两个 agent 实际动手时间占比不高，大头在等客官发话。

### 2.4 一次真实回合的时间账（观测方法：总线时间戳 + 工具调用记录）

以 15 号为例，从客官微信发"15"到交工帖落盘：

| 段 | 动作 | 耗时 |
| --- | --- | --- |
| ① 唤醒 | 微信消息 → 插件投递 → agent 起回合 | 数十秒（含首字延迟） |
| ② 捞单 | `bus_inbox` + 翻 board 找 15 号原文 | 约 30 秒 |
| ③ 审单 | 读档案、算体量、写目录与意见 | 约 6 分钟 |
| ④ 等拍板 | 客官没回三问，直接再发"15"=催办 | 约 4 分钟（空转） |
| ⑤ 成文 | 写 6,900 字 + 校对 + 算哈希 | 约 9 分钟 |
| ⑥ 交工 | 发 result 帖 | 约 1 分钟 |

要点：**②③⑤ 是有效工时，④ 是纯等待，① 是固定开销**。若要提速，只有两条路——把 ④ 的往返砍掉（少问、按默认口径干），或者让 agent 在①上有更短的唤醒路径。其他环节已经没有水分可挤。

### 3.7 成本与计量（已批准的增补项）

已知事实：

- **模型与计费**：本机 agent 只走 SiliconFlow（provider `guiji`）的 DeepSeek-V4-Flash，按 token 计费；**单价与账单从未核对过**（我这边看不到计费口，也无法查询余额）。
- **微信线为省 token 做的裁剪**：人格压到 115 字以内、进度气泡与工具气泡关闭、长结果只进总线而微信只回一行 + 单号。这些都是"减少上下文与输出"的成本手段。
- **云端口径**：掌柜侧拉文件约 45 秒/MB（走 SSH ProxyCommand），这是时间成本而非钱；视频生成在云端，按次计费。
- **计量盲区（必须明写）**：**目前没有任何一单做过 token 或费用计量**，没有采集脚本、没有按单记账、没有月结。原单 WX-04「查微信线花费」正是因为这个盲区一直押着——要查也没有数据源，查就是猜。
- 推论：本报告里所有"耗时"都是墙钟时间，不是成本；谁如果要算投入产出，现有档案里缺这一维，得先补采集。

## 4. 视频工作流

### 4.1 Job 链

```
工坊四卡(人物三视图/背景/场景/提示词六槽)
  → 提交: 生成 video_studio\jobs\<job_id>\job.json + inputs\(front/side/back/background/scene 前缀防撞)
    → 守夜人 studio_daemon2.ps1: 扫 jobs → 校验 → 置 queued
      → 总线发帖(job.json 全文 + 素材路径/SHA/字节)
        → 掌柜云端拉素材 → 生成 → 回传 receipt_<id>.json
          → 守夜人轮询回执 → SHA 对账 → completed / failed
```

## 6. 事故与教训全录（不粉饰）

这一章是给外部 AI 最有价值的部分：每一条都标了起因、处置、防再犯。**包含我自己的错误**。

### 6.1 假回执（6 号）

- 起因：守夜人把"云端回执文件存在"当成"生成完成"，8,267,860 B 的成品数实际来自占位/估算，不是真实回传。
- 处置：以真实回执订正 `job_20261107062914`，旧值保留 `correctedFrom` 字段；补 SHA 对账环节（回执 sha 必须与本地成品 sha 一致才 completed）。
- 防再犯：状态机加 `verifying` 段；"存在即完成"这类推断一律不许写进代码。

### 6.2 误删成品（11 号）

- 起因：uitest 首次运行点错行，把 8 号联调成品删了；脚本没有"列表数 == 磁盘数"的前置断言。
- 处置：云端原件恢复重传；脚本加前置断言 + 删除前二次确认。
- 防再犯：破坏性操作必须先断言环境；自测脚本本身也是被测对象。

### 6.3 sshd 服务被摘（12 号，08:42–14:14，约 5.5 小时断联）

- 起因：`OpenSSH SSH Server` 服务注册从服务列表里消失（只剩 Authentication Agent），程序、配置、主机密钥全在。为何被摘**未查明**，疑安全软件或系统更新。
- 处置：10.4 版 sshd 已无 `-install`，改 `sc.exe create sshd` 手工注册，`start=auto`，LocalSystem；现 Running/Automatic，22 端口在听，掌柜云端实连验收。
- 防再犯：列观察项；账号/服务层无监控是这次的最大教训——5.5 小时没人发现。

### 6.4 闭包悬停（9-补5）

- 起因：PowerShell 事件处理器里用 `GetNewClosure` 后，Enter/Leave 各自锁在私有作用域，读写的不是同一个变量，导致"确认删除"永不还原。
- 处置：改成读写同一脚本作用域变量。
- 防再犯：WPF 事件处理器里别用闭包持有 UI 状态。

### 6.5 先斩后奏（9 号审单欠账）

- 起因：9 号是改代码单（大单），我没先发审单意见就直接开火，事后被指出。
- 处置：台账里认了这条欠账；此后大单先 discuss。
- 防再犯：规矩第 2 条（大单先审单）靠自觉，没有机器兜底——这是流程漏洞之一。

### 6.6 断联与空转（14:28 abort）

- 起因：客官临时有事，回合被 abort，开局帖没发出去，新会话一直没起来。
- 处置：本回合（15:05）重开，补发开局帖，14/16 结案。
- 教训：abort 是"静默丢状态"，没有任何机制记录"这一回合想做什么"，只能靠人回忆。存档包里的 STATUS 文件是唯一补偿。

### 6.7 自动保留误删存档（7 号）

- 起因：里程碑白名单漏登 `0533`，自动保留按"近 5 包"清理时把它连同 0522/0503/0550 一起删了。
- 处置：补进白名单；0520 及以后重新生成；客官点名要保留的备份此后一律进白名单。
- 防再犯：**任何自动清理都必须先列清单、留痕、可撤销**；破坏性规则上线前用小样本演练。

### 6.8 微信会话锁死（通灶）

- 起因：重启后插件 `agents.resume` 接回落盘会话失败，原因被裸 `catch {}` 吞掉，退到 `agents.create`，宿主按 id 发现落盘记录还在，新建一律被拒 → 每条微信都死在"接不回去 + 不许重开"。
- 处置：先把卡住的会话整体移到证据包（未删可搬回），补日志 + 撞车后再试一次 resume。
- 防再犯：裸 catch 是重罪；失败必须留痕。

### 6.9 "白线"系列（4 号，五轮）

- 客官反复说"有条白线"，实际是五个不同根因：①左栏焦点虚线（FocusVisualStyle 默认）②`RailLine` 变量从未 FindName 赋值，主题分支恒不执行 ③页签/工具按钮的 WPF 默认描边从未赋值 ④四个拖图区虚线框写死 #C3D2E2 ⑤传菜口输入条顶边 XAML 写死 #E1E9F1，且第一次改在 `if()` 块内、执行时机不对。
- 教训：视觉问题必须"截图定位到坐标 + 逐条列清单"，不能靠猜；同一条线可能有多个来源。"你说还有线"这类模糊反馈，要主动要红圈/坐标。

## 8. 自评（**以下全是主观判断，非事实，供外部 AI 参考后自行判断**）

### 8.1 三大瓶颈

1. **吞吐被"人"卡死**。agent 不能自起回合，客官是唯一唤醒通道。他不在线，整条链停摆；他一句话，两个 AI 才动。15.6 小时里执行密集但总量受限于客官的在线时长与耐心。这是结构性瓶颈，不是优化能解决的——只能靠"把等待变成批量"（一次给多单）和"把唤醒做成低摩擦"（微信已是最低摩擦）。
2. **验收标准是散文，不是断言**。规矩写得细（七段模板、证据三件套），但都是人读的；没有 schema 校验、没有回归基线。结果：同一条线改五轮、同一个坑踩十次（BOM、图标缓存、尺寸跳）。11 号的 uitest 是唯一像样的机器断言，起步太晚。
3. **状态无单一事实源**。总线、台账、STATE_LOG、SUPPLEMENT、STATUS、handoff 六个文件各写一段，靠人写摘要同步。本报告本身就是在补这个洞。状态一散，新会话开局就要读五份文件，且必然有冲突（比如台账缺 6 行）。

补充（排第四）：**账号/服务层无监控**。sshd 被摘 5.5 小时才发现，属于"系统级失明"。

### 8.2 优化猜想（按性价比排序）

1. **一个机器可读的 `state.json` 单一事实源**：每单一行（编号/状态/证据路径/最后更新），所有摘要文件从它生成。成本低，收益大，直接消灭"台账缺行""STATUS 与实际冲突"。
2. **回合外守护进程**：把"看总线、捞单、判断优先级"从人工唤醒里拆出来——岗哨已做了一半，缺的是"能自己起回合"。这条路客官没批（全自动唤醒），属于待议。
3. **UI 回归断言化**：uitest 扩成"关键视图快照 + 尺寸/颜色/数量断言"，每单交工自动跑一遍出 JSON。13 号的规矩草案正指向这里，应该批。
4. **低风险单免审**：现在所有大单都走审单-确认，来回两趟；可以按"是否可逆 + 是否动钱/账号/数据"分类，可逆的小改直接干、事后报备。
5. **破坏性操作的统一护栏**：自动清理、批量删除这类，统一"先列清单 → 演练 → 可撤销"三段，写进基础设施而不是每个脚本自己实现（7 号的老路）。

### 8.3 一句话

这套东西的工程完成度不低（16 单、253 条档案、5 个存档包、一条跑通的视频链），真正拖住它的是**协作协议的人肉程度**：所有"应该由机器保证的事"目前都由两个 AI 靠自觉和记忆保证。外部 AI 如果只给一条建议，我建议就盯着这个。

### 8.4 给外部 AI 的五个具体问题（客官可以直接拿这段去问）

1. 以"单人 + 双 AI、agent 不能自起回合"为约束，这套协作协议里**哪三条规矩应该被机器执行取代**？给出替代设计（谁校验、校验什么、失败怎么办）。
2. 交给你的"单一事实源"应该长什么样？请给字段清单与更新时机，并说明它如何同时服务：新会话开局、验收入口、外部诊断输入。
3. 现有验收靠"读散文 + 看截图"。请设计一套**成本可接受**的断言式验收（窗口应用、PowerShell/WPF 环境、无 CI），指明最小可行的 5 条断言。
4. 单据史里 17 轮返工，哪些是**单子写得不合格**（缺对象/范围/验收标准），哪些是**执行侧缺陷**？请分别给出模板修订与工程护栏。
5. 这台机器没有服务监控，出过一次 5.5 小时断联。在不引入重型监控栈的前提下，给出一个 30 分钟内能落地的健康检查方案（含检查项、告警通道、误报处理）。
