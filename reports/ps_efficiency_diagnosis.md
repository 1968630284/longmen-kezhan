# PowerShell 5.1＋WPF 开发效率专项诊断

> 依据：项目主报告、STATE_LOG、SUPPLEMENT_1418、xiaozhu_DACHU_STATUS 四份材料。
> 诊断边界：未检查现役脚本源码，未进行运行环境实测。
> 本文为完整三层诊断，非后续 agent 间转发摘要；建议不代表新增操作授权。

**结论：PowerShell 5.1＋WPF 这条路线还能继续用，当前没有足够证据支持立即重写；但“继续维护一个不断打补丁的单文件”不值得延续。** 最划算的做法是先保留 WPF 和现有业务链，把开发方式改成“可定位的布局、明确的状态、可隔离的测试、自动生成的交工证据”，再用一批实际改动判断是否迁移。

现有瓶颈更像是：**看不清控件和状态 → 猜着修改 → 重启整应用 → 人工截图核对 → 再返工**。PowerShell 的动态类型、事件作用域和较弱的重构支持会放大这个问题，但改成 C# 并不会自动消除模糊需求、错误测试和运行版本不明。

以下用 **【材料支持】** 表示四份文件中有记录，用 **【推断】** 表示我的工程判断，用 **【估算】** 表示尚未实测的成本。这里没有检查现役源码，因此不能断言某个函数或布局结构就是实际根因。

## 第一层：不换技术栈，按性价比榨干开发效率

### 1. 先给布局和运行状态装“观察窗口”，减少盲写。性价比最高。

【材料支持】[主报告](D:/tmp/nailong/reports/project_summary_20261107.md)记录白线问题经历五轮，涉及焦点样式、未绑定的控件变量、默认描边和硬编码颜色；这说明“看见一条线”与“知道哪个控件负责”之间存在明显断层。

【推断】这类时间主要花在定位，而非 PowerShell 执行速度。具体做法：

- 给会被修改或测试的控件设置稳定的 `Name`／`AutomationId`，不要靠按钮文案或屏幕坐标识别。
- 增加仅开发模式启用的诊断功能：鼠标选中一个区域后，显示控件类型、名称、父级、实际尺寸、边距、边框和颜色来源。
- 截图自动附上视图名、主题、DPI、窗口尺寸和运行版本；视觉反馈用编号区域定位。
- 颜色、边框、焦点样式集中到资源字典；能使用 `DynamicResource` 的主题属性就统一使用，避免切主题时逐个控件补颜色。

第一版不必造完整可视化设计器。能“列控件树＋标出选中控件边界＋导出属性”，就能解决不少盲改。

### 2. 建立安全、短小的回归集，先验证行为，再扩大覆盖。

【材料支持】11 号出现过误删真实成品、按钮计数误判、窗口最小化导致点击失败；[现状补遗](D:/tmp/nailong/archive/20261107_1418/SUPPLEMENT_1418.md)明确记录了这些问题。因此，当前测试工具本身还不能作为稳定的验收基础。

具体做法是分三类检查：

| 检查层 | 适合检查什么 | 执行时机 |
|---|---|---|
| 不开窗口的检查 | PS 语法、BOM、配置、Job／回执解析、状态转换 | 每次相关修改后 |
| 用测试数据打开窗口 | 四视图、尺寸、溢出、主题、按钮状态 | 布局和交互修改后 |
| 真实链路检查 | 冷启动、微信应答、总线递送、视频回传 | 修改对应链路或发布前 |

删除测试必须操作专用测试成品，按 `job_id` 和路径核实目标。UIA 操作前检查窗口是否可见、目标是否唯一、状态是否满足；操作后等待**预期条件**，不要只固定等待几秒。

【推断】截图适合发现布局问题，语义断言适合确认行为，两者互补。像“悬停后显示确认、离开后还原、点击后仅移除指定成品”这样的断言，比数几个按钮更有价值。

### 3. 把三至五分钟的验证回路拆开，避免每次都重启全部系统。

【材料支持】报告给出的“重启＋截图＋哈希”一轮约三至五分钟，是直接可优化的固定开销；但没有细分其中哪一步最慢。

具体做法：

- 增加开发入口，例如 `-Dev -View Outputs -DataRoot <测试目录>`，直接进入目标页面，使用固定数据。
- 纯逻辑修改先跑无 UI 检查；布局修改只重建目标视图；启动、全局资源、插件和线程相关修改再完整重启。
- 让启动器自动完成：解析检查 → 启动 → 等待窗口就绪 → 检查目标视图 → 截图 → 输出结果。
- 自动记录各步骤耗时，先找出三至五分钟到底花在启动、人工操作还是证据整理上。

【推断】XAML 和主题资源可以做有限的开发态重载，但**不建议一开始做整脚本热更新**。事件重复注册、旧计时器和旧闭包残留会制造更难定位的问题；重载视图必须有明确的卸载、取消订阅和资源释放过程。正式交付仍需一次干净进程的验证。

### 4. 取消“单文件开发”，保留“单入口启动”；按改动热点渐进拆分。

【材料支持】现役约 133 KB，已包含聊天、视频工坊、成品、协作台、主题和状态保存。

【推断】133 KB 本身不是必须迁移的规模，但这些职责继续混在一个文件里，会增加 agent 每次定位和改动的上下文成本。

建议拆成这些职责，而不是机械地按行数分文件：

- 启动与依赖装配。
- XAML 和主题资源。
- 各视图的构建及事件绑定。
- Job、回执、成品等业务操作。
- 文件读写、总线、日志和状态持久化。
- 测试与诊断入口。

先提取边界清楚的纯逻辑，再提取视图。业务模块不要隐式操作全局控件，也不要靠加载顺序碰巧得到变量。每次只迁出一块，保持启动入口和数据格式兼容。

如果确有单文件分发需求，可以由开发源文件生成发布脚本；**单文件交付不要求单文件开发。**

### 5. 把 UI 状态和耗时操作从零散事件里收回来。

【材料支持】悬停失效的根因是 `GetNewClosure()` 让不同事件读写了不同作用域；报告还记录了恢复失败被裸 `catch` 吞掉的问题。

具体做法：

- 每条成品记录持有独立状态，例如当前是否处于删除确认态；Enter、Leave、Click 都访问同一个明确对象。
- 事件处理器只负责“读取输入、调用动作、更新状态”，不要承载大段业务流程。
- 网络请求、文件传输、ffmpeg 等耗时工作放到后台 runspace 或进程；通过 Dispatcher 更新 UI，后台代码不直接修改控件。
- 外部调用统一记录任务号、耗时和错误；重试必须有上限。
- 对状态转换和回执处理先加严格校验，避免一次性给整份旧脚本开启严格模式造成大量兼容问题。

【推断】这里是 PowerShell 的实际弱项之一：类型与作用域问题更容易拖到运行时才暴露。不过，对目前规模仍然可以通过明确接口和状态对象控制，不必立即上复杂框架。

## 第二层：什么时候迁移，迁到哪里，成本多大

**首选迁移方向是 C# WPF，前提是产品继续面向 Windows 桌面。**

【推断】现有界面、WindowChrome、DPI、UIAutomation 和桌面集成都能延续；C# 能补上编译期检查、类型约束、异步编程、调试和重构能力。迁移收益主要来自开发工具和可维护性，不是“C# 必然让窗口快很多”。

以下是我建议的**迁移触发判据**。阈值是决策建议，不是行业定律；先实施上面几项，再观察约十个有代表性的改动：

| 触发条件 | 如何判断 | 对应动作 |
|---|---|---|
| PowerShell 特有缺陷持续出现 | 作用域、动态类型、事件生命周期问题仍反复造成返工 | 优先迁移状态与业务逻辑 |
| 开发反馈仍然太慢 | 目标页面的自动验证仍常超过两分钟，且主要耗在启动／加载而非人工等待 | 比较 C# 原型的实际回路 |
| 小改动经常波及多个视图 | 模块化后仍难隔离依赖，回归范围不断扩大 | 迁移 UI 结构与状态管理 |
| 明确需要更复杂的桌面能力 | 大列表、并发任务、取消恢复、安装升级等已进入近期需求 | 在相关功能扩张前迁移 |
| 平台目标改变 | 明确需要浏览器访问或跨平台桌面 | 重新比较 Web、Avalonia 等路线 |

不会因为文件超过某个字节数就迁移，也不会因为一次白线修了五轮就迁移。那些问题可能来自定位方式和需求变化，换语言仍会发生。

### 迁移成本估算

【估算】假设保留现有文件协议、功能范围和视觉设计，Windows 环境可构建 .NET，且不包含安装器、跨平台和新视频功能：

| 范围 | 有经验开发者的有效工时 |
|---|---:|
| 提取协议、固定测试数据和关键回归基线 | 1–3 人日 |
| 做一个 C# WPF 代表视图，验证启动、主题、数据读取和交互 | 2–4 人日 |
| 迁移其余视图、事件与状态保存 | 4–8 人日 |
| 联调、冷启动、DPI、回归及回滚演练 | 2–5 人日 |

合计约 **9–20 人日**，一人日按六至八小时有效工时理解，区间置信度偏低。两名 AI 的协作墙钟时间不能据此直接折算：验收等待、环境问题、UI 细节都会改变周期；源码检查后才能缩小估算。

### 建议的分步路径

1. 固定 Job、回执、总线和状态格式，建立测试数据及回归检查。
2. 新建 C# WPF 壳，选择“成品列表”作为代表视图：它能同时检验列表、播放器、删除状态和主题能力。
3. 新壳先只读真实数据，写操作使用测试目录；旧应用仍保留回退能力。
4. 迁移一个视图，验证一个视图，逐步接入真实写操作。
5. 完成全链测试后切换；过渡期避免两个应用同时写同一份业务状态。

PowerShell 可以继续保留为部署、诊断和维护脚本，没必要把所有脚本都翻译成 C#。

除非已有明确的新平台需求，否则我不优先推荐 Electron、Tauri 或纯 Web：它们会引入前后端通信、桌面桥接及新的构建部署链。Avalonia 在跨平台成为真实需求时更值得比较。

## 第三层：大厨的流程，哪些应由机器代劳

这里的目标应是**减少重复核对、搜证和整理**。现有“改代码先审单”的规则仍有效，不能借提效自行绕过。

| 性价比顺序 | 可机器化部分 | 具体办法 |
|---|---|---|
| 1 | 交工证据收集 | 一次命令生成改动清单、语法检查、测试结果、截图、哈希和运行版本；汇总成短交工帖 |
| 2 | 接单完整性检查 | 检查对象、范围、验收项和授权版本是否齐全，只列缺失字段，减少反复翻总线 |
| 3 | 文件占用与补丁校验 | 改前 claim 并记录基线哈希；改后核对实际变更范围，防止另一会话覆盖或替换错位置 |
| 4 | 按改动选择验证 | 根据布局、逻辑、启动链路等改动类型选择检查集；涉及公共依赖时扩大回归 |
| 5 | 任务检查点 | 执行前、修改后、自测后记录停点；回合中断后先核对磁盘状态，避免重做 |
| 6 | 授权与结案核验 | 授权绑定任务修订号；缺必需证据不能进入待验收，执行方不能自行写成已验收 |

尤其值得改的是**审单的组织方式**：让机器先收集受影响文件、基线版本、依赖和已有测试，大厨再给出真正需要判断的风险与方案；不要把大量查文件的时间混进“思考六分钟”。掌柜验收也应先读自动检查结果，再核对需求和视觉效果，不必重新计算所有哈希。

交工状态建议明确成三档：

- **已修改**：磁盘文件已变，静态检查通过。
- **已验证**：指定测试通过，运行版本确认。
- **已验收**：掌柜或你按职责批准结案。

【材料支持】桥修复长期待重启、微信配置改了未生效，说明这三个状态确实需要分开。

我的优先投入顺序是：**先做开发态定位、隔离测试和自动验证入口，再模块化，最后评估迁移。** 用接下来一批改动记录“定位耗时、修改耗时、验证耗时、返工原因”；如果定位与验证明显缩短，PowerShell＋WPF 就仍有经济性。如果剩余返工主要稳定地落在动态类型、事件生命周期和异步组织上，再迁 C# WPF，收益才有清楚的证据。
