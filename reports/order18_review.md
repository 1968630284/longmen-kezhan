## 3) 开发态入口可行性 → 方案（推荐**命令行参数**）

推荐 `-Dev` 开关（不选环境变量、不选快捷键）：

- 参数：`param([switch]$Dev)` 已有 param 块（1–6 行），加一行即可；启动器 `launch_app.vbs` 走 `wscript` 不传参，正式路径天然不受影响（**静默启动零改动**）。
- 环境变量不可取：vbs 拉起的进程继承的是用户环境，一旦 `setx` 就永久生效，做到"默认关"要额外的清理逻辑，风险更大。
- 快捷键不可取：热键要常驻事件，正式模式下这本身就是要避免的残留。
- 硬要求（写进实作单的验收）：
  1. 非 `-Dev` 启动时**不注册任何开发事件、不建计时器、不留闭包**；
  2. 开发功能全部收敛在 `if ($Dev) { ... }` 一个块里，用独立函数，不读写 UI 状态变量——**9-补5 的坑**：PowerShell 闭包（`GetNewClosure`）会把状态锁进私有作用域，Enter/Leave 读写不一致导致"永不还原"。开发态若要高亮/还原，状态一律放 `$script:` 作用域。
  3. 单实例互斥：`-Dev` 建议同时允许 `-NoMutex`（已有参数），否则调试必须关掉正式窗口。
  4. 互斥名不变，别为开发另起互斥名，避免任务栏出现两个图标。

## 4) MVP 范围建议 → **改一条：第一版不进主程序**

GPT 提的三件（导出控件树 / 点选标边界 / 截图带元信息）**都能用外部 UIA 工具做，零侵入**：

- 现有的 `tools\uitest\Uitest.ps1` 已经证明 `.NET UIAutomation` 在这台机器上不需要装任何东西就能跑。
- 导出控件树：UIA `TreeWalker` 遍历，直接拿 ControlType / AutomationId / Name / BoundingRectangle / IsOffscreen，**不需要脚本配合**。Name/Margin/BorderThickness 这类 WPF 属性 UIA 拿不到，需退回 `FindName` 反射——那也只能对已命名的 101 个控件取，属第二阶段。
- 点选标边界：`ElementFromPoint` + 一个透明覆盖窗（`AllowsTransparency` + `Topmost`）画框，可完全在工具侧实现。
- 截图元信息：工具侧先枚举窗口（视图名可用当前可见的 Grid 名判断）、读 `live_theme.txt`、`Get-DpiForWindow`、脚本 SHA、时间，再截图，**不用改主程序**。

第一版不做（明确砍）：
- 完整可视化设计器、拖拽改属性 —— 这不是调试需求，是造 IDE；
- XAML 热重载 —— 事件重复注册 + 旧计时器残留，属于 GPT 自己也警惕的坑；
- 主题资源重构 —— 见第 2 条，是独立工程，不塞进定位工具。

**为什么要改这一条**：18 号单的前提是"减少盲改"，而盲改的最大成本是"重启整应用"。外部工具不碰主程序，就用不着为工具本身承担重启与回归风险；等工具证明好用，再谈是否把其中一部分搬进 `-Dev`。
